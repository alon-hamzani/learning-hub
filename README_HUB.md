# Learning Hub v3.0 – מדריך הפעלה והסבה

זהו **קוד React אמיתי** לפלטפורמת לימוד מרובת משחקים, המהווה הרחבה של פרויקט Cloud v2.0. רכיבי משחק הכפל נשמרים במאגר יחד עם תיקוני הסנכרון, ההתקדמות והבדיקות. כרגע מותקן משחק אחד: `multiplication-quest`.

> מדריך התקנה: יש להשלים את ההגדרות המתוארות בפרויקט חדש. האתר המחובר נבדק בנפרד; בדיקות מקומיות אינן תחליף לאימות פריסה.

## מה התווסף?

- **בית מרכזי**: ספריית משחקים אישית שמציגה רק משחקים פעילים שהמשתמש מורשה אליהם, עם הודעה למי שאין לו משחקים.
- **שני סוגי הרשאות נפרדים**: אישור פלטפורמה (`app_users.status`) + הרשאת משחק (`user_game_permissions`). חשבון מאושר ללא משחקים רואה בית ריק. חשבון Pending לא נכנס כלל.
- **ממשק ניהול**: לשוניות Users, Games, Analytics; מתג לכל משחק בדף המשתמש; רשימת משתמשים מורשים בדף המשחק; שינוי שם, תיאור, אייקון, סטטוס פעיל והקצאת משחקים; דוחות לפי משחק.
- **נתונים נפרדים**: `game_progress` לכל משחק ולכל פרופיל תלמיד; `game_sessions.game_id` ו־`activity_events.game_id`; `game_results` לתוצאות מדורגות ו־`game_events` לאירועים גנריים במשחקים עתידיים. נתוני המשחק הישן מועתקים למבנה החדש ללא מחיקה.
- **אבטחת נתונים**: RLS בכל טבלאות המשחקים ו־PostgreSQL RPC לחישוב ציונים, עם בדיקה בזמן הקריאה/כתיבה; mutation של הרשאות דרך Edge Function מאומתת בלבד.
- **נתיבי כתובת**: `#/home`, `#/games/multiplication-quest`, `#/admin`. נתיב משחק בלתי מורשה מוביל להודעת חסימה.

## 1. לפרויקט Supabase חדש לגמרי

1. פתח פרויקט ב־https://supabase.com/dashboard והגדר Google OAuth (פירוט ב־`README_CLOUD.md`).
2. פתח **SQL Editor** והרץ, **לפי הסדר**:
   - `supabase/migrations/20261030_cloud.sql`
   - `supabase/migrations/20261030_learning_hub.sql`
   - `supabase/migrations/20261030_audit_fixes.sql`
   - `supabase/migrations/20261030_server_privileges.sql`
   - `supabase/migrations/20261030_sync_safety.sql`
   - `supabase/migrations/20261030_admin_summary.sql`
3. Google OAuth: ב־Google Cloud Console צור Web OAuth Client והוסף URI מסוג `https://PROJECT_REF.supabase.co/auth/v1/callback`. הגדר Client ID ו־Client Secret בספק Google של Supabase.
4. ב־Supabase Auth > URL Configuration הוסף את הדומיין שבו יפורסם המשחק (Netlify או GitHub Pages).
5. הגדר ושלח פריסה לשלוש Edge Functions: `admin-action`, `notify-approval`, `admin-game-action`. שמור את `RESEND_API_KEY` ו־`EMAIL_FROM` **רק** ב־Supabase Functions Secrets. ניתן לעשות זאת דרך Dashboard או Supabase CLI.
6. Admin אוטומטי: `alon.hamzani@gmail.com` רק אחרי הזדהות Google מאומתת; אין לתת הרשאות לפי המייל המוצהר בדפדפן.
7. בקשת הצטרפות חדשה **לא** מקבלת אוטומטית הרשאה למשחק. האדמין מאשר את המשתמש ומסמן את המשחק הרצוי בכרטיס המשתמש.

## 2. אם כבר הפעלת Cloud v2.0 על Supabase

1. **גבה תחילה את הנתונים**. רצוי ליצור Project ניסיוני ולהריץ בו עותק של הנתונים כדי לבדוק את המיגרציה. הקובץ הוא מיגרציה *מוסיפה* ואסור להריץ שוב את מיגרציית v2 הישנה.
2. הרץ **רק** `supabase/migrations/20261030_learning_hub.sql` ב־SQL Editor. המיגרציה רצה כטרנזקציה עם BEGIN/COMMIT.
3. הקובץ מוסיף `games`, `user_game_permissions`, `game_progress`, `game_results`, `game_events`, מוסיף `game_id` לסשנים, מתאים RLS ומעדכן את RPC `finalize_game`.
4. המיגרציה מעתיקה את `student_profiles.snapshot` ל־`game_progress` עבור המשחק הנוכחי, ומותירה את המקור לגיבוי. ציונים, XP, הישגים והיסטוריה נשמרים. סשנים קודמים משויכים אוטומטית ל־`multiplication-quest`.
5. למשתמשים **שכבר היו מאושרים לפני המיגרציה** ניתנת אוטומטית הרשאת המשחק הראשון כדי שלא ייחסמו בעקבות השדרוג. משתמשים חדשים דורשים הקצאה ידנית. Super Admin יכול לגשת לכל המשחקים.
6. פרסם את הפונקציה הנוספת `admin-game-action`. שתי הפונקציות הקודמות נשארות ללא שינוי.
7. העלה את קוד React החדש ל־GitHub/Netlify, הגדר את משתני הסביבה ושגר גרסה. בדוק שהמשחק נשמר לאחר מעבר בין הבית למשחק.
8. אל תמחק את טבלת `student_profiles` או את עמודת `snapshot` הישנה; היא נשמרה כגיבוי, אך חסומה כעמודה בפני משתמשי API רגילים.

**סייג חשוב:** נתוני `localStorage` מהגרסה הראשונה, לפני Cloud v2, לא מועברים בידי המיגרציה הזו; צריך כלי ייבוא נפרד, לאחר הזדהות בעלי הפרופילים. הנתונים הקיימים בתוך Supabase Cloud v2 כן מועתקים.

## 3. GitHub Pages – פרסום באמצעות GitHub Actions

1. פתח Repository חדש ב־GitHub והעלה את *כל* תוכן הפרויקט, כולל `.github/workflows/deploy.yml` (לא את קובץ ZIP עצמו).
2. Repository Settings → Secrets and variables → Actions → New repository secret. הגדר את שני המשתנים **הציבוריים**: `VITE_SUPABASE_URL` ו־`VITE_SUPABASE_PUBLISHABLE_KEY`.
3. Repository Settings → Pages → Build and deployment → Source = **GitHub Actions**. לא לבחור Deploy from a branch.
4. Push ל־`main` יפעיל בנייה ופריסה של `dist`. הנתיבים משתמשים ב־hash, כך שלינקים ישירים למשחק עובדים גם ב־GitHub Pages.
5. לאחר ההעלאה, העתק את כתובת האתר ל־Supabase Authentication → URL Configuration כ־Site URL / Redirect URL.

אפשר גם לחבר את ה־Repository ל־Netlify עם Build Command=`npm run build`, Publish Directory=`dist`, ולהגדיר את שני משתני `VITE_` תחת Environment variables.

הפעלה מקומית (Node.js 22+):

```bash
npm install
npm run dev
npm run build
npm test
```

**לעולם אין לחשוף בדפדפן/ב־GitHub את `service_role`, `SUPABASE_SECRET_KEYS`, `RESEND_API_KEY`, `GOOGLE_CLIENT_SECRET`.** מפתח Supabase Publishable הוא ציבורי ומותר לכלול אותו בבנייה; ההרשאות חייבות להיאכף ב־RLS וב־Edge Functions.

## 4. הוספת המשחק הבא

1. צור קומפוננטת React חדשה שמקבלת `initialProfiles` ו־`cloud` (כמו `src/App.tsx`). היא צריכה להשתמש ב־`cloud` לכל סשן, ניסיון, הישג ושמירת פרופיל. הממשק `onModuleEvent(studentId,eventKind,payload)` מאפשר אירועים מותאמים ללא שינוי בסכמת הענן. משחקים חדשים עשויים לדרוש פונקציית חישוב ציון ייעודית בשרת (ה־RPC הקיים בודק שאלות של לוח הכפל בלבד).
2. ייבא ורשום אותה ב־`src/games/registry.ts` תחת מזהה `module_key` ייחודי, למשל `reading-adventure`.
3. פרסם את קוד ה־React המעודכן לאתר.
4. ב־Admin → Games Management → רישום משחק חדש, הזן מזהה `game_id`, את אותו `module_key`, שם, תיאור ואייקון. לאחר שהקוד פורסם, סמן Active.
5. ב־Users Management → המשתמש → סמן Checkbox להקצאת המשחק, גם אם הוא כבר Approved.
6. מודול חדש מקבל רשומות עצמאיות ב־`game_progress` ושיוך נפרד ב־`game_sessions`. הוא לא משנה את תוכן המשחק הראשון.

רישום **מטא-דאטה לבדו לא יוצר משחק חדש**. עדיין צריך לבנות את המשחק, להוסיף אותו ל־registry ולפרסם את הקוד. GitHub Pages מגיש קבצים סטטיים: מנגנון האבטחה מגן על הנתונים ועל השימוש דרך הפלטפורמה, אך אינו יכול למנוע מהציבור להוריד את קובצי JavaScript של משחק שכבר פורסם. אם יש צורך לשמור גם את קוד המשחק חסוי, צריך פתרון אירוח עם שרת שמאמת בקשות לקבצים.

## 5. בדיקות לפני פתיחה לציבור

- חשבון Pending: חסום ואינו יכול לקרוא Games, Sessions ו־Progress; מקבל מייל Approval פעם אחת.
- חשבון Approved ללא משחקים: מציג הודעה נעימה וללא כרטיסים.
- Admin מקצה משחק: הכרטיס מופיע לאחר רענון/בדיקה מחודשת.
- Admin מסיר משחק: הכרטיס נעלם, קישור `#/games/ID` אינו נגיש, ו־API לקריאת/כתיבת נתוני המשחק נחסם ב־RLS, כולל RPC הסיום.
- משחק Deactivated: המודול מוסתר ונחסם למשתמשים רגילים גם אם הוקצתה להם הרשאה.
- משחק קיים: השיעורים, עולם הכפל, הניקוד, המשחקים המשלימים ושיאי הילדים נותרו כפי שהיו; הנתונים הקודמים נמצאים ב־`game_progress`.
- שני חשבונות Google שונים לא יכולים לקרוא האחד את נתוניו של האחר.
- שלושת אזורי האדמין חסומים למשתמש רגיל הן ב־UI והן ב־Edge Function.
- צפייה ממכשיר שני עם אותו חשבון Google והיסטוריה זהה (לאחר סיום שמירה וטעינה מחדש).
- הוספת משחק שני: דרך registry + קטלוג + הרשאה, בלי שינוי ב־RLS ובמסכי התשתית.

### מגבלות ידועות

- שמירות משתמשות בגרסה אטומית בשרת. שינוי ממכשיר עם גרסה ישנה נחסם ומוצגת בקשה לרענון; אין מיזוג אוטומטי של שני מסעות שהתנהלו במקביל. מחיקת פרופיל היא פעולה מפורשת בלבד.
- אין תור Offline: כשל ברשת מוצג כהודעת שמירה; חזרו למסך הבית רק לאחר שחזר חיבור האינטרנט.
- המערכת בודקת הרשאות ב־RLS בכל קריאה וכתיבה, וב־UI בריענון, במיקוד החלון ובבדיקה מחזורית (כל 30 שניות). שינוי מוצג בריענון הבא, לא דחיפה מיידית.
- קריאת לוחות הניהול משתמשת בטווחי שרת של 500 רשומות ובתצוגת 25 רשומות בעמוד. סיכומי פעילות מחושבים בשרת. כרגע כל הטווחים נטענים לזיכרון לצורך סינון וייצוא; במערכות גדולות יש להעביר גם חיפוש וייצוא לעיבוד בשרת.
- כמו בגרסת Cloud v2, שאלות אינן נחתמות בשרת ולכן אפשר תאורטית לזייף תוצאות אישיות באמצעות בקשות מיוחדות. תפקיד RLS הוא למנוע פגיעה במשתמשים אחרים וגישה בלתי מורשית, לא להבטיח מניעת רמאות במשחק.
- לא נבדקה התקנת npm או Build מלא בסביבת יצירת הקבצים, עקב היעדר גישה ל־npm registry. בדיקת תחביר AST ובדיקות מחולל התרגילים כן בוצעו. פרסום בפרויקט אמיתי דורש בדיקת `npm run build` ותרחישי הגישה לעיל.
- לילדים קטנים, השתמשו בחשבון Google של ההורה/המבוגר, ואספו רק את המידע הנדרש ללמידה, לרבות הודעת פרטיות והסכמה מתאימה לפני הפצה רחבה.

## עדכון תיקוני הבדיקה המקיפה

בפרויקט שכבר כולל את ארבע המיגרציות הראשונות יש להריץ רק `20261030_sync_safety.sql` ואז `20261030_admin_summary.sql`, לפני פרסום הלקוח החדש. המיגרציות אינן מוחקות התקדמות. גרסה ישנה של לקוח אינה יכולה לעקוף את כתיבת הגרסאות; לאחר הפריסה יש לרענן לשוניות ישנות.

ארבע פונקציות השרת נמצאות במאגר. `email-delivery-check` היא פונקציית אבחון מוגנת במפתח שרת בלבד, עם נמען ותוכן קבועים ומפתח מניעת כפילויות. אין להכניס מפתחות שרת ללקוח או למאגר. אין לקרוא לה כחלק מבדיקות אוטומטיות חיות. `supabase/config.toml` מתעד את מצב השער הקיים: האימות מתבצע בקוד הפונקציות, כולל בדיקת תפקיד וסטטוס בפעולות ניהול. סודות נשמרים ב־Supabase בלבד.
